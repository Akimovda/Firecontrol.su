# Память проекта: firecontrol

Этот файл — рабочая память проекта. Сюда записываются: суть проекта, принятые решения,
договорённости, известные проблемы и ссылки на артефакты. Обновляется по ходу работы.

## Что это за проект

Инструменты для публикации статей на сайт WordPress (тематика — пожарная безопасность:
СОУЭ, сигнализация и т.п., судя по примерам в коде) через REST API, сразу с SEO-полями
(Yoast / Rank Math) и FAQ-блоком (видимый + JSON-LD Schema.org).

## Файлы

- `wp_publish.py` — CLI-скрипт публикации.
  - Вход: markdown-файл (`--file`) или stdin.
  - Конвертирует markdown → HTML, добавляет FAQ (видимый `<h2>/<h3>/<p>` блок + `FAQPage` JSON-LD).
  - Создаёт пост в WP через `wp-json/wp/v2/posts`, по умолчанию статус `draft`.
  - Умеет: категории/теги (создаёт при отсутствии), обложку (локальный файл или URL),
    SEO title/description/focus keyword под Yoast или Rank Math (автоопределение плагина
    через `wp-json/` namespaces, либо явно `--seo-plugin`).
  - Настройка через переменные окружения: `WP_URL`, `WP_USER`, `WP_APP_PASSWORD`
    (WordPress Application Password, не основной пароль).
- `wp-seo-rest-meta.php` — must-use плагин для WordPress (кладётся в `wp-content/mu-plugins/`,
  активация не нужна). Регистрирует защищённые SEO-мета-поля Yoast/Rank Math с
  `show_in_rest => true`, иначе REST API не может их записать. Доступ на запись — только
  пользователям с правом `edit_posts`.

## Важные зависимости между файлами

Без установленного на сайте `wp-seo-rest-meta.php` скрипт `wp_publish.py` всё равно создаст
пост и FAQ, но SEO-поля молча не запишутся (скрипт это детектит и предупреждает в выводе).

## GitHub Pages — статичное зеркало страниц сайта

В `docs/` лежит статичное HTML-зеркало (сделано `wget --page-requisites --convert-links`)
части страниц firecontrol.su — для GitHub Pages (репозиторий публичный, значит и
опубликованное зеркало видно всем). Источник: `/tmp/mirror_urls.txt` в момент создания
(2026-08-08) содержал 10 URL: главная, `/about_company/`, `/contact/`,
`/licenses-and-certificates/`, `/fire-audit/`, `/evacuation-plans/`,
`/fire-alarm-systems/` и 3 последние опубликованные статьи (id 901, 904, 908).
Наполняется постепенно, не всё сразу — по решению пользователя.

Чтобы добавить страницы позже: тот же `wget` на новый URL с `--directory-prefix=docs
--no-host-directories --convert-links --page-requisites --span-hosts --domains=firecontrol.su`.

Включить показ: в настройках GitHub-репозитория Settings → Pages → Source: Deploy from
branch → Branch: `main`, папка `/docs` → Save (я не могу включить это сам — нет токена
для GitHub API/`gh auth`, только push по SSH).

## Известные проблемы

### Форма обратной связи не долетает до Telegram-бота (с ~16 марта 2026)

Формы на страницах услуг (`class="forma"`) шлют `$.post` на
`wp-content/themes/firecontrol/send.php` (обычный PHP-файл темы, не WP REST —
редактировать можно только через FTP/SSH/файловый менеджер хостинга или
wp-admin → Редактор тем; у нас нет туда доступа, только WP REST API из `.env`).

**Диагностировано (2026-08-07):**
- Отправка в Telegram сделана через `fopen("https://api.telegram.org/bot{$token}/...")`
  БЕЗ проверки результата — если `fopen()` не удаётся (например, хостинг блокирует
  исходящие HTTPS до Telegram, или изменился `allow_url_fopen`), скрипт молча идёт
  дальше и ничего не логирует.
- `$return_arr` не заполняется явным "ok" при успехе — заполняется только при ошибке.
  Если ни одна проверка (телефон/mail()/amoCRM) не споткнулась, скрипт отдаёт `json_encode([])`
  = `[]`. Фронтенд (`theme.js`) проверяет только `data.frm_check == 'error'` — при `[]`
  это `undefined`, и пользователь видит "Ваше сообщение отправлено!", даже если Telegram
  ничего не получил. Это системная проблема UX, не только текущего бага.
- Проверили напрямую через Telegram Bot API (`getMe`, `getChat`, тестовый `sendMessage`) —
  токен бота `@FireControl_bot` жив, доступ к обоим чатам (группа "🔥FireControl" и личный
  чат) есть, тестовое сообщение доставлено успешно. **Значит проблема НЕ в боте/токене/чате,
  а в обрыве сети/PHP-окружения именно на сервере firecontrol.su** (не может быть проверено
  без SSH/FTP-доступа к серверу).

**Что нужно для финального фикса:** доступ по SSH/FTP, чтобы проверить
`allow_url_fopen` и связность `curl -v https://api.telegram.org` с сервера, и заменить
`fopen()` на `curl` с проверкой результата (по образцу уже рабочего блока отправки в amoCRM
в том же файле).

### Секреты в открытом виде в коде темы

`send.php` содержит захардкоженные боевые секреты: токен Telegram-бота, токен мессенджера
Max, и полноценный долгоживущий Bearer-токен amoCRM (права `crm, files, files_delete...`,
годен примерно до 2030 года). Файл лежит в `wp-content/themes/firecontrol/` — при любой
утечке исходников (мисконфиг, бэкап) это полный доступ к CRM. Секреты уже были показаны
в чате с Claude при диагностике — рекомендована ротация всех трёх токенов и вынос их из
кода темы в переменные окружения. См. [[feedback-secrets-handling]] — то же правило,
которое действует и для наших собственных `.env`, должно применяться и на стороне сайта.

## Файлы (доп.)

- `wp_audit.py` — SEO-аудит опубликованных постов через REST API: тонкий контент,
  SEO title/desc, обложка+alt, alt у картинок в тексте, дубли H1/отсутствие H2.
  Сортирует по приоритету (скор). `--csv`/`--json` сохраняют полный отчёт.
- `wp_linkmap.py` — карта внутренних ссылок между постами и страницами: считает
  входящие/исходящие internal-ссылки, находит "сироты" (0 входящих). Отдаёт только
  сырые данные графа — смысловые рекомендации "откуда сослаться" делаются вручную/LLM
  по выгруженным заголовкам и выжимкам контента.

  `/special-technical-conditions/` (СТУ), `/videonablyudenie/`, `/fire-alarm-systems/`,

  эвакуации плотно связаны друг с другом и с услугой).

## Рабочий процесс для новых статей (сложился по ходу публикаций)

1. Из присланного текста убирать служебный мусор: домены-сноски источников
   (типа "grad.center" отдельной строкой), пометки темы сайта (дата обновления,
   "аудиоверсия" и т.п.) — не вставлять их в тело статьи как видимый текст.
2. Исправлять опечатки в присланном тексте при переносе в markdown (смысл не менять).
3. Заголовки секций — `##` (H2), никогда `#` (H1) — H1 страницы это заголовок поста.
4. Фото для обложки подбирать самостоятельно (Pexels/Unsplash, свободная лицензия),
   визуально проверять перед использованием (скачать и посмотреть через Read),
   указывать источник в `--image-caption` и осмысленный `--image-alt`.
5. Искать в тексте естественные места для внутренних ссылок на страницы услуг сайта,
   особенно на страницы-сироты без входящих ссылок (см. `reports/linkmap.json`
   и раздел про linkmap выше) — по одной-две ссылки на статью, не форсированно.
6. SEO title ≤60 символов, description ≤155, фокусный ключ по теме статьи.
7. Категории/теги — сначала проверять существующие через API, переиспользовать
   подходящие, создавать новые только когда действительно нет соответствия.
8. Публикация всегда как draft (по умолчанию у wp_publish.py) — не публиковать сразу.

## Правило: секреты

Секреты (WP_APP_PASSWORD, токены и т.п.) — только в `.env`, никогда не в память (memory)
и не в код. `.env` обязательно должен быть в `.gitignore`.
