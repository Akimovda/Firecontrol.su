договорённости, известные проблемы и ссылки на артефакты. Обновляется по ходу работы.

## Что это за проект

СОУЭ, сигнализация и т.п., судя по примерам в коде) через REST API, сразу с SEO-полями
(Yoast / Rank Math) и FAQ-блоком (видимый + JSON-LD Schema.org).

## Файлы

- `wp_publish.py` — CLI-скрипт публикации.
  - Вход: markdown-файл (`--file`) или stdin.
  - Конвертирует markdown → HTML, добавляет FAQ (видимый `<h2>/<h3>/<p>` блок + `FAQPage` JSON-LD).
  - Создаёт пост в WP через `wp-json/wp/v2/posts`, по умолчанию статус `draft`.
  - Умеет: категории/теги (создаёт при отсутствии), обложку (локальный файл или URL),
    SEO title/description/focus keyword под Yoast или Rank Math (автоопределение плагина
    через `wp-json/` namespaces, либо явно `--seo-plugin`), «Автор публикации»
    (ACF-поле `avtory`, по умолчанию Михайлов Владислав — `--specialist-id`/`--no-author`
    чтобы сменить/отключить).
  - Настройка через переменные окружения: `WP_URL`, `WP_USER`, `WP_APP_PASSWORD`
    (WordPress Application Password, не основной пароль).
- `wp-seo-rest-meta.php` — must-use плагин для WordPress (кладётся в `wp-content/mu-plugins/`,
  активация не нужна). Регистрирует защищённые SEO-мета-поля Yoast/Rank Math с
  `show_in_rest => true`, иначе REST API не может их записать. Доступ на запись — только
  пользователям с правом `edit_posts`.

## Важные зависимости между файлами

Без установленного на сайте `wp-seo-rest-meta.php` скрипт `wp_publish.py` всё равно создаст
пост и FAQ, но SEO-поля молча не запишутся (скрипт это детектит и предупреждает в выводе).

## GitHub Pages — статичное зеркало страниц сайта

В `docs/` лежит статичное HTML-зеркало (сделано `wget --page-requisites --convert-links`)
части страниц firecontrol.su — для GitHub Pages (репозиторий публичный, значит и
опубликованное зеркало видно всем). Источник: `/tmp/mirror_urls.txt` в момент создания
(2026-08-08) содержал 10 URL: главная, `/about_company/`, `/contact/`,
`/licenses-and-certificates/`, `/fire-audit/`, `/evacuation-plans/`,
`/fire-alarm-systems/` и 3 последние опубликованные статьи (id 901, 904, 908).
Наполняется постепенно, не всё сразу — по решению пользователя.

Чтобы добавить страницы позже: тот же `wget` на новый URL с `--directory-prefix=docs
--no-host-directories --convert-links --page-requisites --span-hosts --domains=firecontrol.su`.

Включить показ: в настройках GitHub-репозитория Settings → Pages → Source: Deploy from
branch → Branch: `main`, папка `/docs` → Save (я не могу включить это сам — нет токена
для GitHub API/`gh auth`, только push по SSH).

**Важно про SEO-ценность этого зеркала:** сам по себе дословный `wget`-снимок на другом
домене НЕ даёт ссылочного веса firecontrol.su — это дублированный контент, а не
независимый авторитетный источник, и не заменяет реальный линкбилдинг (каталоги,
партнёрские упоминания, Яндекс.Бизнес). Ценность зеркала — версионированный бэкап
контента для нас самих, не инструмент роста SEO.

**Баг canonical (исправлено 2026-08-08):** `wget --convert-links` при мирроринге
перезаписывал уже существующий (от Yoast) тег `<link rel="canonical">` на
самоссылающийся относительный `href="index.html"` — то есть каждая зеркальная страница
объявляла себя каноничной вместо оригинала на firecontrol.su, что создавало риск
путаницы с дублями контента. Прогнан скрипт, вручную вернувший canonical на абсолютный
URL оригинала (`https://firecontrol.su/<slug>/`) на всех 25 файлах в `docs/`.
**При каждом новом `wget`-мирроринге эту правку нужно повторять** — сам wget её
перезапишет заново, если не проверить и не поправить после каждого прогона.

## Известные проблемы

### ~~Форма обратной связи не долетает до Telegram-бота~~ — ИСПРАВЛЕНО 2026-08-08

Формы на страницах услуг (`class="forma"`) шлют `$.post` на
`wp-content/themes/firecontrol/send.php` (обычный PHP-файл темы на сервере, не WP REST).

**Причина (диагностировано 2026-08-07):** отправка в Telegram была сделана через
`fopen("https://api.telegram.org/bot{$token}/...")` без проверки результата — при неудаче
скрипт молча продолжал работу. `$return_arr` заполнялся только при ошибке, поэтому при
полном успехе (или при силентном фейле шага без собственной проверки) ответ был пустым
`json_encode([])` = `[]`, а фронтенд (`theme.js`, проверяет только `data.frm_check ==
'error'`) показывал "Ваше сообщение отправлено!" в любом случае — то есть форма могла
годами молча не доставлять сообщения, и никто бы не заметил.

**Фикс (2026-08-08):** получен верный SSH-доступ (см. раздел выше), сделан бэкап
(`send.php.bak-20260808` в той же папке на сервере), блок отправки в Telegram переписан
с `fopen()` на `curl` с проверкой HTTP-кода и `curl_error()` (залогирует через `error_log`
при неудаче), явно выставляется `frm_check = 'error'` только если ОБА получателя
(группа и личный чат) не получили сообщение. Проверено end-to-end реальной отправкой
через форму — сообщение подтверждённо дошло в Telegram.

### Формат телефона изменён + добавлена honeypot-защита от спама (2026-08-08)

По запросу пользователя маска телефона изменена с `+7 (999) 999 - 9999` на
`+7(999)999-99-99` — правки внесены СИНХРОННО в двух местах (иначе форма перестаёт
принимать любые номера, как в предыдущем баге):
- `theme.js` (строка с `$("input[name=phone-at]").mask(...)`) — JS-маска ввода.
- `send.php` (`$mask = "+7(XXX)XXX-XX-XX";`) — серверная валидация.

**Важно:** `theme.js` подключается с версией в query-string (`theme.js?v3`), которая
НЕ была захардкожена под автообновление WordPress — при правке файла обязательно
увеличивать версию (`?v3` → `?v4` и т.д. в `footer.php`), иначе у посетителей с закэшированным
JS форма будет присылать номер в старом формате, а сервер — его отклонять. Это уже один
раз произошло сразу после правки маски и было исправлено бампом версии.

Обнаружено, что антиспам в `ban.php` (чёрный список IP) полностью закомментирован и
фактически не работает. Вместо его реанимации добавлено **honeypot-поле**
(`name="website-at"`, визуально скрыто через `position:absolute;left:-9999px`,
`tabindex="-1"`, `aria-hidden="true"`) — вставлено в три места, где встречается форма
(`class="forma"`): `footer.php` (попап консультации, вызывается из шапки сайта),
`sidebar-service.php` (сайдбар "Разместить заказ" на всех страницах услуг),
`page-contact.php` (страница контактов). В `send.php` в начале обработки POST — если
`website-at` не пусто, скрипт молча возвращает `[]` (как при обычном успехе) и завершает
работу, ничего никуда не отправляя — бот не понимает, что его вычислили.
Проверено end-to-end: пустой honeypot — сообщение доходит; заполненный — не доходит,
при этом ответ сервера одинаковый в обоих случаях.

Бэкапы на сервере (в той же папке `wp-content/themes/firecontrol/`):
`send.php.bak-20260808`, `send.php.bak-20260808-mask`, `send.php.bak-20260808-honeypot-server`,
`theme.js.bak-20260808`, `footer.php.bak-20260808-honeypot`,
`sidebar-service.php.bak-20260808-honeypot`, `page-contact.php.bak-20260808-honeypot`.

### `wp-seo-rest-meta.php` не был установлен на сервере + не работал для `page` (2026-08-08)

Обнаружено при попытке проставить SEO-поля странице `/evacuation-plans/` (id 105, `page`,
не `post`): запись через REST молча не проходила. Причины сразу две:
1. Папки `wp-content/mu-plugins/` на реальном сервере вообще не существовало — плагин из
   этого репозитория никогда не был туда залит (хотя `wp_publish.py` для ПОСТОВ и без него
   прекрасно работал — SEO-мета для `post` регистрирует сам Yoast из коробки).
2. Даже если бы был установлен, старая версия плагина регистрировала мета-поля только
   для `register_post_meta('post', ...)`, без `'page'` — а у Yoast свой REST-схема для
   `page` эти поля не выставляет вообще (проверено через `OPTIONS /wp-json/wp/v2/pages`).

**Исправлено:** `wp-seo-rest-meta.php` обновлён (регистрирует ключи для `post` И `page`
в цикле) и реально развёрнут в `wp-content/mu-plugins/` на сервере через SCP. Проверено:
`OPTIONS /wp-json/wp/v2/pages` теперь отдаёт все 6 ключей (Yoast+RankMath), запись
SEO-полей странице 105 подтверждена. Теперь SEO-правки через REST доступны для ЛЮБОЙ
из 25 страниц услуг, не только для постов.

ровно по тому же принципу exact-url, что и наши мёртвые — но у НИХ это реально работает,

из своего кода. Наши цели ждали того же трюка, но никто не написал вызов `ym(...)`.

обработчик `.forma`), добавлена строка:
```js
if (typeof ym === 'function') {
    ym(53166577, 'hit', location.pathname + '?form_success=1');
}
```

РЕАЛЬНЫМ путём страницы, помеченный маркером `form_success=1`, то есть разбивка по конкретной
услуге/странице получается бесплатно через стандартный отчёт Метрики «Содержание → Страницы»
(фильтр по вхождению `form_success=1`) — без необходимости заводить 12+ отдельных целей под

пробел — при точечных `content.replace()` через REST **всегда сверять точную
подстроку через `repr()` перед `assert`**, иначе тихий провал или неверная замена.

## Правило: секреты

Секреты (WP_APP_PASSWORD, токены и т.п.) — только в `.env`, никогда не в память (memory)
и не в код. `.env` обязательно должен быть в `.gitignore`.

**Техническая ловушка:** `WP_APP_PASSWORD` в `.env` содержит пробелы (стандартный формат
WordPress Application Password, `xxxx xxxx xxxx xxxx xxxx xxxx`), значение НЕ взято в
кавычки. Обычный `source .env` в bash из-за этого разбивает строку по пробелам и
переменная обрезается до первого фрагмента — REST-запросы тихо получают неверный
пароль (401 `rest_forbidden_context`), при этом bash сыплет незаметные ошибки
`command not found: <фрагмент>` для остальных кусков. Разбирать `.env` через Python
(`k, v = line.split('=', 1)`), а не через `source`, когда нужен именно `WP_APP_PASSWORD`.
